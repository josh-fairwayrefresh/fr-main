# Engineering Documentation System

## Decision
Define and adopt a stable, minimal engineering documentation system for Fairway Refresh that orients new engineers, distinguishes project vs upstream vs historical docs, and uses a small, persistent index at `docs/README.md`.

## Context
The project contains product code, many sample READMEs, board notes, and large upstream documentation (Zephyr, vendor SDKs). New engineers need a short, reliable entrypoint and predictable doc structure that survives repository layout changes.

Iteration during this design session produced a concise `docs/README.md` that serves as the visible index and guide for engineers joining the project.

## Rationale
- New engineers benefit most from a single, human-readable index that points to authoritative product docs and practical HOWTOs; long governance documents or heavy review workflows slow onboarding.
- Upstream documentation (RTOS, vendor datasheets, SDKs) should be referenced, not duplicated, to reduce maintenance burden and avoid stale copies.
- Historical and experimental materials must remain discoverable but explicitly marked so they are not mistaken for current guidance.
- Documentation should be practical: short, example-rich, runnable when appropriate, and annotated when claims need verification.

## Consequences
- Positive:
  - Fast onboarding: a new engineer can read `docs/README.md` in minutes and find next steps.
  - Lower maintenance: fewer governance rules; docs are small and kept near the code they document (HOWTOs live with samples/components).
  - Clear separation of responsibility: product-level facts are the accepted authority for operations and engineering decisions.
- Required behaviors:
  - Treat product-level authoritative docs as the operational truth until updated.
  - When a doc contains a claim that cannot be immediately verified, add an inline `To Be Verified` note with the verification step.
  - Mark obsolete content as `Status: archived` and place it in an archive area or leave an archive header.
  - Keep HOWTOs and examples short and runnable; link rather than copy upstream docs.
- Not adopted:
  - No formal review or publishing process is required by this decision; administrative processes are intentionally omitted to keep the system lightweight.
